## Step 1 — Tenant schema indexes

**Files:** `prisma/tenant/schema.prisma`, `prisma/tenant/migrations/20261016161807_add_perf_indexes/migration.sql`

Added:
- `Customer`: `@@index([status, createdAt])`
- `Visit`: `@@index([date, status])`, `@@index([roundId, date])`, `@@index([technicianId, date])` (existing single-column indexes on `serviceId`/`propertyId`/`roundId`/`servicePlanId`/`technicianId` kept)
- `Invoice`: `@@index([status, dueDate])`
- `Payment`: `@@index([status])`
- `Complaint`: `@@index([status])`

Migration was generated with `prisma migrate dev --schema prisma/tenant/schema.prisma` against a scratch schema (`TENANT_MIGRATION_URL=...&schema=_tenant_scratchN`) on the project's real Postgres instance, then applied and verified there, per the header instructions in `schema.prisma`. The final migration file contains **only the 7 `CREATE INDEX` statements above** — see "Schema drift found and fixed" below for why the first two generation attempts produced a much larger, unrelated diff.

### Schema drift found and fixed (not part of the perf work itself)

The first `prisma migrate dev` run against a clean scratch schema produced a migration containing the 7 intended indexes *plus* a large unrelated diff: dropped/recreated `RoundTechnician` foreign keys, a dropped `IntegrationOutbox` index, a dropped default on `BusinessSettings.preCleanReminderTimings`, and ~10 `ALTER COLUMN ... SET DATA TYPE TIMESTAMP(3)` statements across `BusinessSettings`, `ChatMessage`, `Device`, `Notification`, `StripeSession`, `SupportReport`, `Visit`, `WebhookEvent`.

Root cause, traced via `git log`/the migration SQL itself: several migrations in this project's history (`20260721000003_setup_steps_9_12`, `20260923000000_stripe_integration`, `20261002000000_chat_message`, `20260930000000_visit_started_arrived_at`, `20261006000000_ghl_oauth`, `20261006000002_integration_outbox`, `20261013000001_mobile_gaps`, `20261013000002_mobile_notifications`) were **hand-written SQL rather than generated by `prisma migrate dev`** — identifiable by `IF NOT EXISTS`/`IF NOT EXISTS` guards that Prisma's own generator never emits. Those hand-written migrations:
- Consistently used `TIMESTAMPTZ` for timestamp columns (the better Postgres practice — avoids timezone ambiguity), while `schema.prisma` declared plain `DateTime` (Prisma's default maps that to `TIMESTAMP(3)`, no timezone). Every hand-added `createdAt`/`receivedAt`/`expiresAt`/`completedAt`/`ghlTokenExpiresAt` column had this mismatch.
- Added `BusinessSettings.preCleanReminderTimings` with `DEFAULT '{}'` in SQL, but `schema.prisma`'s field had no `@default([])`.
- Created `RoundTechnician`'s foreign keys with `ON DELETE CASCADE ON UPDATE CASCADE` (explicitly, per that migration's own comment: *"CASCADE keeps the join table consistent without requiring extra application-side cleanup"*) — but `schema.prisma`'s relation fields didn't declare `onDelete: Cascade`, so Prisma's default (`RESTRICT`) is what the schema implied.
- Added an `IntegrationOutbox_status_createdAt_idx` index directly in SQL that was never declared as an `@@index` on the `IntegrationOutbox` model in `schema.prisma`.

None of this was caused by the perf-indexes work — `schema.prisma` and the real applied-migration state have been silently diverging since those commits, and nothing catches it because tenant migrations aren't run through `prisma migrate dev` at runtime (a custom runner applies the committed SQL files directly — see the schema file's own header comment). It only surfaced now because generating a *new* migration requires Prisma to diff against the full historical SQL replay.

**Fix: `schema.prisma` was corrected to match the intended, already-live behavior** (not the other way around — the hand-written SQL reflected real intent, documented in its own comments):
- `RoundTechnician.round`/`.technician` relations: added `onDelete: Cascade, onUpdate: Cascade` to match the live FK behavior.
- `IntegrationOutbox`: added `@@index([status, createdAt])` to match the live index.
- `BusinessSettings.preCleanReminderTimings`: added `@default([])` to match the live column default.
- `BusinessSettings.ghlTokenExpiresAt`, `ChatMessage.createdAt`, `Device.createdAt`, `Notification.createdAt`, `StripeSession.expiresAt`/`completedAt`/`createdAt`, `SupportReport.createdAt`, `Visit.startedAt`/`arrivedAt`, `WebhookEvent.receivedAt`: added `@db.Timestamptz` to match the live column type.

After these fixes, the migration was regenerated from scratch (new scratch schema, deleted the two earlier draft migration folders) and now contains **only the 7 `CREATE INDEX` statements** — verified by inspecting the final `migration.sql` directly. `prisma generate --schema prisma/tenant/schema.prisma` was re-run afterward to refresh the generated client; `tsc --noEmit` and the full test suite were re-verified clean after.

**Nothing else needs to happen for this specific drift** — it's resolved in `schema.prisma` itself now, not deferred to a follow-up migration. Flagging it here only so the next person who runs `prisma migrate dev` on this schema doesn't get confused by a large unexplained diff — if you do see one again, it means something new has drifted (e.g. another hand-written migration), not a regression of this fix.

## Step 2 — Customer list & detail fixes

**File:** `src/services/customer.service.ts`

- `getCustomers()`: the `status === "HOLD"` branch no longer fetches every customer and filters/slices in JS. The `paymentHold` condition is now pushed into the Prisma `where` (`properties.some.visits.some.{paymentHold:true, status:{in:OPEN_VISIT}}`, merged with `roundId` when both filters are supplied so combining HOLD + a round filter still works), and HOLD now goes through the same `count` + `findMany({take, skip})` path as every other status.
- `getCustomers()`'s `listInclude`: `payments` sub-include capped to `take: 1` (only `payments[0]` was ever read). `properties` left unchanged — the active-property fallback logic there wasn't touched to avoid an untested behavior change.
- `getCustomerDetail()`: the `visits` sub-include now has `orderBy: {date:"desc"}, take: 50` at the query level instead of fetching the customer's entire visit history and slicing to 50 in JS twice (`visitHistory` and `payments.rows`). **Decision: `payments` (top-level) was deliberately left uncapped** — `outstandingBalance`/`lastPaymentDate` need the full payment history, and capping to 50 would have silently dropped older unpaid invoices for long-tenured customers.

Before/after: `getCustomerDetail` for a customer with hundreds of visits went from one query joining round/technician/invoice/payment/issues across every visit ever recorded, to the same join capped at 50 rows, ordered by the DB.

## Step 3 — Cross-round planner batch endpoint

**Files:** `src/routes/rounds.ts`, `src/services/round.service.ts`

New endpoint: `GET /rounds/planner/occurrences?roundIds=a,b,c&from=YYYY-MM-DD&to=YYYY-MM-DD` → `{ roundId, occurrences: OccurrenceSummary[] }[]`, one entry per requested round (empty array if no matching visits, no 404 for unknown round IDs — batch semantics, not single-resource semantics). `roundIds` are comma-separated, trimmed, empty segments dropped, capped at 50. `from`/`to` validation mirrors the existing single-round endpoint (at least one bound, 90-day max range).

New service method `round.service.ts#listOccurrencesForRounds` issues exactly **one** `prisma.visit.findMany({ where: { roundId: { in: roundIds }, date: {...} } })` regardless of how many rounds are requested, then groups in-memory by `(roundId, date)` reusing the existing `aggregateStats` helper. The old single-round endpoint (`GET /rounds/:id/planner/occurrences`) is untouched.

Full request/response contract is in the frontend handoff doc (`2026-10-16-frontend-handoff.md`) — copy from there if you need the exact shape for a client integration.

## Step 4 — Debt service: N+1 elimination + SQL bucket filtering

**Files:** `src/services/debt.service.ts`, `src/routes/debt.ts`

- **N+1 fix:** `getBoard()`'s per-customer `message.findFirst` loop (`Promise.all(customerIds.map(...))`) replaced with one `prisma.$queryRaw` using `SELECT DISTINCT ON ("customerId") ... ORDER BY "customerId", "createdAt" DESC` against `Message`, guarded to skip entirely when there are zero outstanding invoices.
- **Bucket filtering pushed into SQL:** `getBoard()` previously fetched every `SENT` invoice and filtered buckets (`BAD_DEBT`, `ON_HOLD`, `FAILED_GC`, `DUE_BEFORE_CLEAN`, `SEVEN_DAYS_OVER`, `FOURTEEN_DAYS_OVER`, default) with a JS `.filter()` switch. Every bucket condition is now a Prisma `where` clause (built incrementally onto a `customerWhere: Prisma.CustomerWhereInput` object assigned once to `where.customer`, rather than repeated spread-reassignment — the latter didn't typecheck cleanly against Prisma's generated relation-filter types and was fixed post-agent, see "Fixes applied after parallel implementation" below).
- **Pagination added:** `getBoard(bucket, roundId?, paymentMethod?, page?, pageSize?)` — new params, default `page=1`, `pageSize=50` (max 100). Return shape changed from a bare array to `{ rows, pagination: { page, pageSize, total, totalPages } }` — **this is a response-shape change**, called out explicitly in the frontend handoff doc. `GET /debt/board` in `src/routes/debt.ts` was updated to parse `page`/`pageSize` query params and pass the full object through.
- **`getKpis()`:** fetch-all-then-`.reduce()` replaced with `aggregate`/`count`/`findMany({distinct:["customerId"]})` per bucket condition — no behavior change, same output shape.

Before/after: the debt board's last-contacted lookup went from N queries (one per customer with an overdue invoice) to 1. Bucket filtering and pagination now happen in Postgres instead of loading every `SENT` invoice into Node on every page load.

## Step 5 — Dashboard & reports: JS aggregation → SQL groupBy/aggregate

**Files:** `src/services/dashboard.service.ts`, `src/services/reports.service.ts`

- `dashboard.service.ts#getKpis()`: complaint severity bucketing → `complaint.groupBy({by:["severity"], _count:true})`. Monthly revenue and unpaid-visit amount → `visit.aggregate({_sum:{price:true}})`. The unpaid-visit **distinct-customer count** (`cleanUnpaidCount`) intentionally stayed a scoped `findMany` (trimmed to drop `price` now that the sum comes from `aggregate`) — deduping by `customerId` across multiple properties can't be expressed as a `groupBy`/`distinct` on `propertyId` alone.
- `dashboard.service.ts#getChartData()`: full completed-visit `findMany` for a 6/12-month range → one `$queryRaw` using `date_trunc('month', v."date")` joined to `Issue`, grouped. Confirmed no `@@map`/`@map` directives exist in `prisma/tenant/schema.prisma`, so Prisma's default PascalCase-table/camelCase-column mapping applies to the hand-written SQL identifiers.
- `dashboard.service.ts#getTechnicianKpis()`: jobs/value → `visit.groupBy({by:["technicianId"], _count:true, _sum:{price:true}})`; complaints → `complaint.groupBy({by:["technicianId"], _count:true})`. `issueCount` per technician intentionally kept as a scoped `findMany` (bounded row count for one period) rather than a raw-SQL rewrite.
- `reports.service.ts#getTechnicians/getRevenue/getSummary`: same pattern — `visit.groupBy`/`aggregate` replacing manual `.reduce()`/`Map` grouping. `getRevenue` uses `$queryRaw` with `date_trunc('day', ...)` (verified `Visit.date` is `TIMESTAMP(3)` without timezone in the init migration, so no UTC/local-timezone mismatch vs. the old `date.toISOString().slice(0,10)` bucketing). `getSummary`'s `completedRounds` is a **distinct** count via `visit.groupBy(["roundId"]).length`, not a sum.
- `getVisits`, `getActivity`, `logActivity` in `reports.service.ts` were left unchanged (out of scope — already reasonably scoped).

**BigInt / numeric-string handling:** raw `$queryRaw` results from Postgres return `SUM(...)` as a numeric string (sometimes a number) and `COUNT(...)` as a JS `BigInt`. Both are normalized through `Number(...)` before being placed in response objects, in both `getChartData` and `getRevenue` — `BigInt` fails `JSON.stringify` (`TypeError: Do not know how to serialize a BigInt`), so skipping this conversion would 500 the endpoint the first time any bucket had a non-zero count.

## Step 6 — Per-tenant BusinessSettings cache

**Files:** `src/services/settings.service.ts`, `src/middleware/requireTenantAccess.ts`, `src/routes/settings.ts`, `src/routes/setup.ts`, plus a follow-up fix (below) touching `src/services/customer.service.ts`, `src/services/invoice.service.ts`, `src/services/today.service.ts`.

**As originally implemented (parallel agent):**
- `settingsCache`: an `LRUCache<string, BusinessSettings>` inside `settings.service.ts`, keyed by tenant **schema name**, TTL 30s (matches `profileCache` in `requireTenantAccess.ts`), positive-only (never caches `null`).
- `SettingsService`'s constructor gained a second param, `schemaName: string`. `createSettingsService(prisma, schemaName)`.
- `requireTenantAccess.ts` now also sets `req.tenantSchemaName = profile.tenant.schemaName` alongside `req.tenantPrisma`.
- `getSettings()` checks the cache first; `writeSettings()` (the sole mutation seam) deletes the cache entry for that schema after a successful upsert.
- Only two call sites actually construct `SettingsService`: `src/routes/settings.ts` and `src/routes/setup.ts` — both updated.

**Gap found after integration — and fixed:** the plan's original audit assumed 8+ call sites reading `BusinessSettings` directly (not through `SettingsService`) would benefit from this cache: `customer.service.ts`, `invoice.service.ts` (×3), `today.service.ts`, plus several routes. None of those call `SettingsService` — they call `prisma.businessSettings.findFirst()` directly. As first implemented, the cache therefore only sped up the settings/setup *admin* routes, not the actual hot paths (customer detail, invoice creation, today's work) the plan was written to fix.

**Fix:** added a second, separate cache in `settings.service.ts` — `getCachedBusinessSettings(prisma: TenantPrismaClient)`, exported — keyed by **prisma client instance** via a `WeakMap`, not by schema name string. This avoids threading `schemaName` through every service constructor: `getTenantPrismaForSchema()` (`tenant-prisma-manager.ts`) returns the *same* client instance per tenant schema for as long as it stays in its own LRU (max 100), so instance identity is a reliable per-tenant cache key for practical purposes — a miss after eviction just costs one extra DB read, never a cross-tenant leak. Same 30s TTL, same positive-only rule. `writeSettings()` invalidates both caches (`settingsCache.delete(this.schemaName)` and `directSettingsCache.delete(this.prisma)`).

Wired into:
- `customer.service.ts#getCustomerDetail` (was `this.prisma.businessSettings.findFirst()`)
- `invoice.service.ts` — `getInvoice`/render, `createInvoice`, `previewInvoice` (3 sites, all previously used a narrow `select`; now read the full cached row and destructure the needed fields — the row is small, see `BusinessSettings` model, so this isn't a meaningful over-fetch)
- `today.service.ts#getTodaysWork` (was `select: { lastClosedDate: true }`)

**Deliberately NOT wired into caching**, even though they also call `businessSettings.findFirst()` directly — flagging the reasoning so it isn't "fixed" by a future refactor without re-reading this:
- `today.service.ts#closeDay` — reads `lastClosedDate` inside a `$transaction` callback as an idempotency guard immediately before closing the day. A transactional read that gates a mutation must see the current committed state, not a cached value; caching here risks a stale read letting the day be closed twice.
- `src/routes/customers.ts` (mandate setup, ×2), `src/routes/debt.ts` (Stripe payment-link), `src/routes/visits.ts` (GoCardless payment creation) — all read encrypted payment-processor tokens (`stripeSecretKeyEncrypted`, `gocardlessAccessTokenEncrypted`) and connection-status flags (`stripeConnected`, `gocardlessConnected`) to *initiate a real payment or mandate*. These are low-frequency, mutation-adjacent endpoints, not the repeated-per-page-load reads the plan targeted — and caching a "connected" flag or token for 30s on a money-moving path means a disconnect/reconfigure wouldn't take effect for up to 30 seconds. Left as direct reads for correctness on payment-critical code, not for performance.
- `mobile/routes.ts`, `mobile/services/debt-gate.ts`, `routes/ghlWebhook.ts`, `routes/gocardlessWebhook.ts`, `routes/stripeWebhook.ts`, `integrations/ghl/api.ts`, `services/setup.service.ts` — none of these were named in the original plan/audit; webhook handlers in particular resolve the tenant differently (not via `requireTenantAccess`) and verify external payloads, so they were left untouched to avoid introducing risk to integrations outside this plan's scope.

## Fixes applied after parallel implementation (integration pass)

The 5 steps above (2–6) were implemented by parallel subagents working on non-overlapping files, each reporting test/coverage results independently. After integration, a full `tsc --noEmit` + `vitest run` pass found and fixed:

1. **`debt.service.ts` type errors** (10 errors, `TS2322`): the pattern `where.customer = { ...where.customer, badDebt: true }` repeated per switch-case didn't typecheck — TypeScript narrows `where.customer`'s type from the first assignment, and the later reassignments with different literal shapes conflicted with Prisma's generated `CustomerWhereInput`-vs-`CustomerScalarRelationFilter` union. Fixed by building a single `customerWhere: Prisma.CustomerWhereInput` object incrementally and assigning it to `where.customer` exactly once, before the switch. Also needed an explicit `PaymentMethod` cast for the `paymentMethod` query param (was a plain `string`, not the generated enum type). No behavior change — same final `where` shapes, verified by re-running `debt.service.test.ts` (all 53 cases still pass) after the fix.
2. **`today.service.ts` had zero test coverage** (pre-existing — no test file existed for it at all before this work). Since Step 6's follow-up touched `getTodaysWork()`, added `src/services/__tests__/today.service.test.ts` covering that function specifically (cache hit/miss via `getCachedBusinessSettings`, `dayClosed` derivation, KPI/round/technician aggregation from a small visit fixture). `closeDay()` and the file's other untouched helpers remain uncovered — out of scope for this change, flagged here for whoever next touches that file.

Final verification after all fixes: `npx tsc --noEmit` — zero errors. `npm test` (`vitest run`) — **23 files, 332 tests, 0 failures**.
